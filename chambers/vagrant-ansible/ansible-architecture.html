Config management / vagrant-ansible chamber

Vagrant + Ansible: a real machine, described in code

Vagrant conjures the VMs; Ansible turns bare Debian into a running three-tier app over SSH, with no agent on the guests. This is Ansible's honest demo: real hosts, real services, described declaratively and re-runnable to the same end state.

lb / HAProxy web / Flask db / PostgreSQL
The one idea. Ansible is agentless configuration management. The control node connects over SSH, gathers facts, and pushes each host toward a described state with idempotent modules. Nothing runs on the guests; the repo is the source of truth. Run it twice and the second run changes nothing.

Architecture

The topology

Four VMs, three tiers. A load balancer round-robins two web servers that read from one database, all on an isolated private network. The host reaches the load balancer directly.

Two tools, two jobs

Vagrant provisions, Ansible configures

The clean split: Vagrant owns the machines and the network; Ansible owns everything inside the operating system. They meet at SSH.

Vagrant (+ libvirt)

owns: the machines
  • Defines the four VMs from one Vagrantfile (box, memory, cpus).
  • Two NICs per guest: a management NAT for SSH and outbound, an isolated private network for app traffic.
  • Boots them on the libvirt (KVM) hypervisor and manages SSH keys.
  • Lifecycle: up, ssh-config, destroy.

Ansible

owns: the software
  • Connects over SSH using Vagrant's generated config, gathers facts.
  • Applies four roles idempotently: base, database, app, load balancer.
  • Templates config, manages packages/services, wires the tiers together.
  • Re-runnable: a second run is all green.

Concepts

The Ansible building blocks

inventory

Inventory & groups

Hosts organized into groups (loadbalancers, webservers, databases) with a nested webstack child group. Plays target a group; each host carries a private_ip.

role

Roles

Reusable units with tasks/, handlers/, templates/, defaults/. Four here: common, postgresql, webapp, haproxy.

tasks

Tasks & handlers

Tasks converge state with modules. Handlers run once at play end, only if notified, for reactions to change (restart the app, reload HAProxy). flush_handlers forces a restart mid-role.

jinja2

Templates

Jinja2 with full access to facts and vars. The MOTD renders from facts; the app env file from the Vault password; the HAProxy config from the inventory.

secrets

Ansible Vault

The DB password is encrypted in vault.yml and referenced by a non-secret name (the vault-indirection pattern). It is load-bearing: a least-privilege DB user is created with it and the app connects with it.

plugin

Custom filter

A filter plugin (haproxy_backends) turns the webservers group into HAProxy server lines, looking each private IP up in hostvars. Logic that belongs in code, not a template.

galaxy

Collections

External modules pulled via requirements.yml: community.postgresql for the DB, community.general for ufw/haproxy/timezone, ansible.posix.

tags

Tags

Each role is tagged (common, db, web, lb), so a single tier can be applied with --tags instead of the whole play.

delegation

Delegation

delegate_to runs a task on a different host than the play targets. The rolling deploy drains a web node by running the HAProxy module on the load balancer.

common: base packages, a deploy user, MOTD from facts, ufw (allow SSH first, then default-deny), sshd hardening. postgresql: install + psycopg2, listen on all interfaces, pg_hba scram rule, then create the DB, a least-privilege user, the table, grants, and seed. webapp: Flask app + a Vault-templated env file + a systemd unit. haproxy: config generated from the inventory, health checks, admin stats socket.

Variables

Precedence, low to high

When the same variable is set in more than one place, the highest wins. This is why task deploy can override app_version at run time.

role defaults lowest
inventory / group_vars group
host_vars host
play vars play
extra-vars (-e) highest

Networking

Two networks, on purpose

NetworkInterfaceCarriesReachability

Isolated privateeth1app traffic (lb to web, web to db)guests + host only, forward_mode: none

Ansible reaches the guests over the management NAT; the app tiers talk over the isolated 192.168.56.0/24. The host holds .1 on that bridge, so it can curl the load balancer. ufw allows the app ports only from the private subnet.

The advanced piece

Zero-downtime rolling deploy

deploy.yml with serial: 1 processes one web node at a time. Live traffic never hits a restarting app, because the node leaves the load balancer first.

drain
disable in HAProxy
→
redeploy
new version
→
health
wait /healthz 200
→
re-enable
back in rotation
Why it is zero-downtime. The drain and re-enable talk to HAProxy's admin stats socket, run delegate_to the load balancer (the task executes on the lb, not the web node). Naive serial + restart would 5xx in the window before health checks eject the node. Verified: a curl loop through the whole deploy = zero non-200, version flips live.

The promise

Idempotence

Running the playbook twice reports zero changes on the second run. That is the whole point of describing state instead of scripting steps.

apt update

Marked changed_when: false so a cache refresh is never a "change".

CREATE TABLE

Uses the idempotent postgresql_table module, not a raw query that always reports changed.

seed row

INSERT ... ON CONFLICT DO NOTHING with changed_when tied to the row count.
