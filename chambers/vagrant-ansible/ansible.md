# Ansible, end to end

How the project in this chamber is structured and why. Grounded in the four
roles, the grouped inventory, the Vault-encrypted DB password, the custom filter
plugin, and the rolling deploy under `ansible/`.

## The one idea

Ansible is agentless configuration management: it connects to hosts over SSH,
gathers facts, and pushes them toward a described state with idempotent modules.
No agent runs on the guests; the control node holds the truth. This is why VMs
(not containers) are the honest demo - Ansible's job is to take a bare OS over
SSH and turn it into a running service.

## The layout

```
ansible/
  ansible.cfg            inventory, roles_path, vault file, ssh config
  requirements.yml       collections (community.postgresql, community.general, ...)
  inventory/hosts.yml    groups: loadbalancers, webservers, databases, webstack
  group_vars/
    all/vars.yml         non-secret vars, incl. db_app_password -> vault indirection
    all/vault.yml        ENCRYPTED (vault_db_app_password)
    webservers.yml       web-tier packages
    databases.yml        pg version/paths
    loadbalancers.yml    stats port
  host_vars/lb.yml       per-host: stats credentials
  filter_plugins/        custom Jinja2 filter (haproxy_backends)
  roles/                 common, postgresql, webapp, haproxy
  site.yml               the four-tier play
  deploy.yml             zero-downtime rolling deploy
```

## Inventory and variable precedence

The inventory groups hosts by role and nests `webservers` + `databases` under a
`webstack` child group. Each host carries a `private_ip`. Variables resolve by
Ansible's precedence: role defaults (lowest) < inventory/group_vars < host_vars <
play vars < extra-vars (`-e`, highest). That last one is what `task deploy` uses
to bump `app_version` at run time. `db_host` is computed from the databases group
(`hostvars[groups['databases'][0]].private_ip`), so the app tier always points at
the right database without hardcoding.

## Roles and handlers

Each role is a self-contained unit (`tasks/`, `handlers/`, `templates/`,
`defaults/`). Tasks converge state; **handlers** run once at the end of a play,
only if notified, and are for reactions to change (restart the app when its
config or code changed, reload HAProxy when its config changed). The PostgreSQL
role uses `meta: flush_handlers` to force the restart *mid-role* - the DB must be
listening on all interfaces and know the app's pg_hba rule before the later tasks
create the roles the app will use.

`site.yml` runs the tiers in order, each play `become: true`, each role tagged
(`common`, `db`, `web`, `lb`) so a tier can be applied alone. `pre_tasks` assert
the guests are Debian and that the custom filter plugin loaded.

## Secrets: Ansible Vault

The real DB password lives encrypted in `group_vars/all/vault.yml` as
`vault_db_app_password`. A non-secret name in `vars.yml`
(`db_app_password: "{{ vault_db_app_password }}"`) references it - the **vault
indirection pattern**, so playbooks and templates use `db_app_password` and never
touch the ciphertext. The secret is load-bearing: the PostgreSQL role creates a
**least-privilege** app user (SELECT/INSERT on one table, nothing more) with that
password, and the webapp role templates the same password into the app's
environment file. Change one, break both. The `.vault_pass` here is a lab-only
password committed so a fresh run can decrypt; in production it would come from a
prompt, a file outside the repo, or a secrets manager.

## Templates and the custom filter

Templates are Jinja2 with full access to facts and vars. The MOTD renders from
`ansible_facts`; the app's env file is templated with the Vault password. The
HAProxy config is the interesting one: its backend server lines are generated by
a **custom filter plugin** in `filter_plugins/lab_filters.py`:

```jinja
{% for line in groups['webservers'] | haproxy_backends(hostvars, app_port) %}
    {{ line }}
{% endfor %}
```

`haproxy_backends` walks the web hosts, looks each private IP up in `hostvars`,
and returns `server <name> <ip>:<port> check ...` lines. Authoring a filter is
how you push logic out of templates when a loop needs real code. The template is
written with `validate: "haproxy -c -f %s"`, so a bad render fails the task
instead of a broken HAProxy.

## Idempotence

Running the playbook twice should report zero changes - that is the whole promise.
The usual offenders are shell/query tasks and cache refreshes, handled here
explicitly: `apt update` is `changed_when: false`; the `CREATE TABLE` and the
seed `INSERT ... ON CONFLICT` use `changed_when` tied to the actual statement
result and row count. The second `task provision` being all green is the real
gate, not the first successful apply.

## The rolling deploy

`deploy.yml` is the advanced piece. `serial: 1` processes one web node at a time,
and for each it:

1. **Drains** the node from HAProxy by talking to the admin stats socket
   (`community.general.haproxy`, `state: disabled`, `drain: true`, `wait: true`),
   `delegate_to` the load balancer - the task runs *on the lb* against its socket,
   not on the web node.
2. **Redeploys** the app (`include_role: webapp`), which restarts it with the new
   version via the notified handler.
3. **Waits** for `/healthz` to return 200.
4. **Re-enables** the node in HAProxy.

Because the node is out of rotation before it restarts, live traffic never hits a
restarting app. `task rolling-demo` curls the LB continuously through the whole
deploy and counts non-200s; done right, that count is zero. This is the same
zero-downtime idea as the Istio blue-green chamber, expressed with a load
balancer and Ansible delegation instead of a service mesh.

## The one-paragraph version

Ansible connects to the four VMs over SSH (via a Vagrant-generated ssh config),
gathers facts, and applies four roles idempotently: a common base with firewall
and SSH hardening, PostgreSQL with a least-privilege app user whose password comes
from Vault, a Flask app templated with that password, and HAProxy whose backends
are generated from the inventory by a custom filter. Handlers react to change,
tags scope the tiers, and a `serial: 1` deploy drains each web node from HAProxy
through its admin socket before redeploying, giving a zero-downtime rollout - all
described declaratively and re-runnable to the same end state.
