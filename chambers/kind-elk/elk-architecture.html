The Elastic Stack: making logs searchable

A pipeline that turns a wall of unstructured log text into typed, queryable data. Ship the lines off each node, parse them into fields, store and index them, and explore them. The point is to get from "grep the whole cluster" to "show me every status:500 in the last hour".

INFO WARN ERROR
The one idea. Logs are the third pillar of observability. Metrics say how much / how fast, checks say is it up, and logs say what actually happened, in detail. The Elastic Stack makes that detail searchable, and the step that makes search possible is parsing: turning text into fields.

Components

What each piece does

Four data-plane components plus the operator that runs them. "Beats" is a family of lightweight shippers; Filebeat is the one for logs.

ship

Filebeat (a Beat)

A lightweight agent, one per node (DaemonSet), that tails container log files, enriches each line with Kubernetes metadata (pod, namespace, labels), and forwards it. Beats are the shippers; other members do metrics, uptime, packets.

reads /var/log/containers/*.log
parse

Logstash

The transform stage: a pipeline of input -> filter -> output. Here a beats input receives events, a grok filter carves the text into fields, and an elasticsearch output writes them. This is where raw text becomes structure.

input · filter · output
store

Elasticsearch

The store and search engine: a distributed document database built on an inverted index, so full-text search and field aggregations are fast. Documents live in indices; each field has a mapping (type). This is the heart of the stack.

documents · indices · inverted index
explore

Kibana

The UI: Discover (search), Lens and dashboards (visualize), Dev Tools (raw queries), plus alerting and management. It reads Elasticsearch; a data view tells it which indices to query.

discover · dashboards · dev tools
operator

ECK

Elastic Cloud on Kubernetes runs the whole stack from CRDs (Elasticsearch, Kibana, Logstash, Beat). It generates TLS certs, the elastic superuser, and per-association least-privilege users, and reconciles drift. The recommended path now that the Helm charts are archived.

CRDs · TLS · associations
the skill

Grok

Pattern matching for logs: named regex blocks compose into a pattern that splits a line into fields, with type hints so numbers stay numbers. The teachable "L" in ELK, and why this chamber emits text instead of JSON.

%{PATTERN:field:type}

The parse step

Grok: text to fields

One unstructured line becomes typed, queryable fields. The :int hints make status and latency_ms numbers, so you can range-query and average them.

ERROR 500 GET /healthz 340ms internal server error
grok: %{WORD:level} %{NUMBER:status:int} %{WORD:method} %{DATA:req_path} %{NUMBER:latency_ms:int}ms %{GREEDYDATA:log_message} ↓
level keyword = ERROR status int = 500 method keyword = GET req_path keyword = /healthz latency_ms int = 340 log_message text = internal server error

A line the pattern cannot match is tagged _grokparsefailure and still stored, so parse gaps are findable. Emitting JSON would skip grok with a json filter, which is why text is the interesting case.

Wiring and security

Two hops, two models

ECK auto-wires most connections with TLS and generated credentials. One hop it does not manage, and one least-privilege detail bites everyone.

manual hop

Filebeat → Logstash

NOT an ECK association. You set output.logstash by hand to the Logstash beats service on 5044, plain TCP. TLS on this hop is a cert rabbit hole for a lab.

managed hop

Logstash → Elasticsearch

An ECK association (elasticsearchRefs). ECK injects the host, a generated user, the password, and the CA as env vars the pipeline references. TLS end to end, no manual certs.

The least-privilege gotcha. The user ECK mints for Logstash can only write logstash-* (and ecs-logstash-*) indices. Point the output at app-logs-* and every write fails with 403 security_exception. Fix: name the index under the allowed pattern (this chamber uses logstash-app-*) or grant a custom role. ECK does not hand a superuser to every component.

Elasticsearch data model

The vocabulary

TermWhat it is
documentOne JSON record (one parsed log line), the unit of storage and search
indexA collection of documents (here time-based: logstash-app-YYYY.MM.dd)
field + mappingA key in the document and its type; the mapping decides if you can aggregate or range-query it
inverted indexThe term-to-document structure that makes full-text search fast
shard / replicaHow an index is split and copied across nodes; a single node leaves replicas unassigned (health YELLOW, still fine)
data viewKibana's pointer at one or more index patterns, e.g. logstash-app-*; the prerequisite for querying in the UI
data streamThe newer append-only abstraction over rolling indices for logs and metrics

Declarative / GitOps

Two layers, different reconciliation

The stack self-heals; the dashboards do not. That asymmetry is the whole story of "declarative ELK".

reconciled

The stack

Elasticsearch, Kibana, Logstash, Filebeat as ECK CRDs (YAML). The operator continuously reconciles drift. Full GitOps with Argo CD / Flux. The Logstash pipeline and Filebeat config live inside these CRDs.

apply-on-deploy

ES config

Index templates, ILM policies, ingest pipelines, roles: idempotent PUT to the ES API from CI, or the Elastic Terraform provider, or ECK StackConfigPolicy. Converges on deploy.

not reconciled

Kibana content

Data views, searches, dashboards have no controller. Export to NDJSON, commit, re-_import?overwrite=true in CI. Nothing reverts a UI edit unless you re-import or mark objects managed.
