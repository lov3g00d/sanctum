Monitoring / kind-icinga chamber

Icinga: the check-and-notify stack

Icinga actively runs a plugin against every host and service on a schedule, turns the plugin's exit code into a state, holds that state until it is stable, and notifies on change. It goes and asks. It does not wait to be told.

OK · exit 0 WARNING · exit 1 CRITICAL · exit 2 UNKNOWN · exit 3
The one idea. A monitoring model built on discrete host/service states and notifications on change, driven by an active scheduler. That is the opposite of Prometheus, which scrapes numeric metrics and evaluates alert expressions over a time series. Icinga thinks in states; Prometheus thinks in samples.

Services

The components

Six services make up the stack in this chamber. Icinga 2 is the brain; the rest are state, UI, and optional layers. Icinga 2 never writes SQL directly - state flows through Redis and the Icinga DB daemon.

engine

Icinga 2

The core. Holds the object config, schedules and runs checks, computes states, and fires notifications. Exposes a REST API.

StatefulSet · port 5665 (API) · image icinga/icinga2
state relay

Redis (Icinga DB Redis)

The fast hand-off buffer. Icinga 2 writes live runtime state here; the Icinga DB daemon consumes it. Decouples the engine from the SQL write path.

port 6379 · an Icinga-tuned Redis
state daemon

Icinga DB

Reads runtime state from Redis and persists it to MySQL/MariaDB. This Redis-relay design replaced the older direct-to-SQL IDO.

Deployment · image icinga/icingadb
database

MariaDB

Durable store for history, comments, downtimes, and config. The chart runs one instance per database (Icinga DB, Icinga Web, Director, Kubernetes).

port 3306 · one StatefulSet per DB
web ui

Icinga Web 2

The dashboard. Reads MariaDB (and Redis for live data) to draw hosts, services, problems, and history. Modular: Director, Icinga DB, Kubernetes are modules.

port 8080 · here on http://localhost:18082
k8s collector

Icinga for Kubernetes

A separate daemon that watches the Kubernetes API and syncs resource state (pods, deployments, nodes) into a database for the Kubernetes web module. Complements checks; it does not replace them.

Deployment · image icinga/icinga-kubernetes
config module

Icinga Director (optional)

A web module plus its own database for managing config with import/sync from external sources, deployed to Icinga 2 over the API. The right tool at fleet scale; this chamber instead pushes config through the raw API to keep the model transparent.

Concepts

The object model

Everything in Icinga is a typed object in declarative config. These are the ones you actually write. apply rules are the scaling lever: describe a thousand hosts' checks in a few rules with an assign where expression.

object

Host

A monitored machine or endpoint. Has an address and its own check. Top of the dependency tree; groups services.

object

Service

A specific check on a host. Carries the check_command and scheduling knobs. Where "is /healthz OK?" lives.

command

CheckCommand

How to run a plugin: the executable plus how arguments map to vars.*. Ships in the Icinga Template Library (ITL).

object

TimePeriod

When checks or notifications are active (e.g. 24x7). Must be defined explicitly when conf.d is disabled.

object

User & UserGroup

Notification recipients, each with states and types filters: only tell me about these states and these event kinds.

command

NotificationCommand

What to run to notify (email, chat, a script). Its $macros$ resolve host/service/notification context.

rule

Notification

Binds a command + users + period + filters to a checkable, usually via apply ... to Service with assign where.

grouping

HostGroup / ServiceGroup

Membership sets used for filtering, dashboards, and as targets for apply rules.

meta

apply rule

apply Service "disk" to Host { assign where ... } generates objects across everything matching an expression. Config that scales.

The check pipeline

Exit code to state, soft to hard

The plugin's exit code is the state. A failing check is SOFT at first and only becomes HARD after max_check_attempts retries - which is what stops a single blip from paging anyone. Notifications fire on the HARD transition.

check_interval

How often a stable check runs (15s in this chamber).

retry_interval

Faster recheck cadence while in a SOFT state (5s here).

max_check_attempts

SOFT failures needed before HARD (2 here). The anti-noise dial.

Config as code

Three ways to deliver config

The chart mounts Icinga 2's /etc/icinga2 from a ConfigMap and disables conf.d, so this chamber uses the middle lane: the REST API config-package endpoint.

lane 1

conf.d files

Plain .conf files on disk. Fine for one static node, awkward in a container. Disabled by the chart.

lane 2 · used here

REST API config package

POST /v1/config/packages/<pkg> then POST /v1/config/stages/<pkg> with a files map. Icinga validates and reloads. Version-controllable and scriptable.

lane 3

Icinga Director

A web module + DB that manages config with import/sync and deploys to Icinga 2 over the API. The fleet-scale option.

Gotcha. In config strings $ delimits a macro, so a shell $(date) inside a command throws a macro error. Use Icinga's own macros ($icinga.long_date_time$, $service.output$) or escape a literal $ as $$.

Notifications

The filter chain

A notification only sends when every gate passes - which is exactly the anti-noise design. Miss one and nothing sends, which is the usual reason a "broken" notification is actually a filter.

HARD state change type in filter
Problem / Recovery / ... state in filter
Critical / Warning / OK inside TimePeriod enabled on host, service, user & globally send

Paradigm

Icinga vs Prometheus

Two honest ways to know if something is broken. They are complementary, not rivals - this chamber is the check-and-notify counterpart to the pull-model SLO chamber next door.

Icinga (this chamber)

  • Push model: an active scheduler runs checks.
  • Discrete states: OK / WARNING / CRITICAL / UNKNOWN per host and service.
  • Soft vs hard states suppress flapping before notifying.
  • Notifications on state change, with users, periods, and filters.
  • Plugin-based: any exit-code program is a check.
  • Best for reachability, host/service up-down, black-box checks.

Prometheus

  • Pull model: scrapes numeric metrics on an interval.
  • Time series: labelled samples over time, queried with PromQL.
  • Alerting rules evaluate expressions; Alertmanager routes.
  • SLOs / burn rate fall out of the math naturally.
  • Instrumentation-based: apps expose /metrics.
  • Best for rates, latencies, saturation, trend and capacity.
