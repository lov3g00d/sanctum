# Chamber: kind-k8sgpt

[k8sgpt](https://k8sgpt.ai) triaging a broken Kubernetes workload on kind, with the plain-English
explanation generated by a local model. A deliberately broken deployment and service are applied
to a kind cluster; `k8sgpt analyze` finds the faults with no LLM, and `--explain` routes them
through the local Ollama server for a human-readable diagnosis. No cloud, no API key.

This pairs the `local-llm` chamber (the model server) with a real ops task. k8sgpt's analysis is
largely single-pass, which is exactly the shape a small CPU model handles well: it reads the
cluster deterministically and only asks the model to phrase the fix.

## What it demonstrates

- k8sgpt's deterministic analyzers catching real failure modes (ImagePullBackOff, a service with
  no endpoints) with no model involved.
- `--explain` against a local Ollama backend: the same findings turned into plain-English guidance,
  fully offline.
- A repair loop (`task fix`) that clears the fault and shows the analysis go quiet.
- Two ways to consume k8sgpt beyond the CLI: an **MCP server** (`task mcp`) so Claude Code can
  call its analyze/get-logs/list-resources tools, and the **operator** (`task operator`) doing
  continuous in-cluster scanning into `Result` CRDs.

## Prerequisites

- The repo toolchain: `nix develop` from the repo root (provides `kind`, `kubectl`, `k8sgpt`, `jq`).
- A running Docker daemon (kind builds the cluster in containers).
- For `task explain` only: the `local-llm` Ollama server running on `localhost:11434`. The rest of
  the chamber needs no model.

## Stand up

```sh
cd chambers/kind-k8sgpt
task up            # kind cluster + broken workload + k8sgpt wired to local Ollama
task analyze       # the findings, no LLM
task explain       # the same findings explained by the local model
task test          # deterministic PASS/FAIL: both planted faults must be found
```

Then:

```sh
task fix           # repair the deployment and watch the analysis clear
task status        # the demo namespace
```

## Drive it from Claude Code (MCP)

k8sgpt ships an MCP server, so Claude Code can call its tools (`analyze`, `cluster-info`,
`get-logs`, `get-resource`, `list-events`, `list-namespaces`, `list-resources`, filters) against
the cluster:

```sh
task mcp           # prints the exact `claude mcp add` line (with pinned ports); it does not edit your config
```

`serve` also binds a gRPC (8090) and metrics (8091) port even in MCP mode, so the command pins them
to avoid two sessions colliding on the defaults.

## Operator mode (continuous scanning)

The operator is the in-cluster counterpart to the one-shot CLI: it scans on an interval and writes
every finding as a `Result` CRD.

```sh
task operator          # helm-install the operator + apply the K8sGPT config
task operator-results  # the Result CRDs, one line of detail each
task operator-down     # remove the operator (keeps the cluster + workload)
```

It runs **analysis-only** (`ai.enabled: false`): the operator pod cannot reach the host's Ollama
through the NixOS firewall, and analysis needs no model anyway. Turning on LLM-explained results is a
documented opt-in in [`k8sgpt.md`](k8sgpt.md) (it needs a host firewall rule).

## How it targets the cluster

Every `kubectl` and `k8sgpt` call names the `kind-k8sgpt` context explicitly, and the k8sgpt
backend is written to a chamber-local `.run/k8sgpt.yaml`. Nothing touches your global kube-context
or `~/.config/k8sgpt`.

## Tear down

```sh
task down          # delete the kind cluster and .run/
```

See [`k8sgpt.md`](k8sgpt.md) for how the backend is wired and why the analyze/explain split matters
on a CPU-only box.
